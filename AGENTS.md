# Editing the CMDOP SDK repository

This repository contains the TypeScript and Python SDKs, runnable examples and exported technical
documentation. For editorial work, read [CONTRIBUTING.md](CONTRIBUTING.md) first.

## Editorial scope

You may update `README.md`, Markdown stories in `showcase/` and approved images in `assets/`.
Use ordinary Git commits or pull requests according to your assigned access. No package release,
version bump, package-registry credentials or full SDK build is needed for editorial changes.

SDK code, package READMEs, executable examples, licenses, `docs/`, `tools/`, these instructions,
contribution policy and GitHub workflows are maintainer-owned. Do not change them as part of an
editorial task. The content check is a collaboration check, not a credential-level access boundary.

## Message and evidence

Lead with an understandable outcome: an existing AI can act on a computer its owner controls.
Keep a clear next step to connect an AI or try the SDK. Put detailed setup, method reference,
recipes and troubleshooting in the linked technical documentation. The root README is an entry
point, not another reference manual. Use English and make the text useful without images.

Make claims from current documentation and verified evidence. A conceptual illustration is not
proof of an actual run. Do not invent integrations, usage metrics, stars, completion results,
unlimited plans or release availability. The SDK's MIT license does not describe the whole platform.
Use [cmdop.ai](https://cmdop.ai), [documentation](https://docs.cmdop.ai/reference/sdk) and
the package manifests here for product, setup and version context.

Keep executable code fences unchanged during editorial work. Request a maintainer-validated
example update when needed; runnable sources and the full guide must be corrected together.
Technical docs are exported from the documentation website. Report a correction with the public
page, proposed change and reproducer so a maintainer can fix its source; never patch `docs/` directly.

## Artwork and promotion

Use existing approved assets. New/changed images need a maintainer-recorded SHA-256 in
`tools/approved-assets.json`. Drafts, prompts and rejected candidates stay in the designated
asset workspace until the owner selects a deliverable; do not put them in this repository.
Preserve brand marks, provide useful alt text and check the result on mobile and both themes.

Offer useful examples and stories before an optional invitation to star the repository. No bought
or exchanged stars, incentives, star-gated features, mass requests or messages to stargazers.
Keep stars, repository visits, package downloads and verified use separate. A change in stars
after a post does not establish attribution. Coordinate campaign IDs, timing and observations
with the assigned promotion coordinator; do not create a parallel campaign from a README edit.
Repository editing does not itself authorize social posts, outreach, issue replies or settings changes.

## Work and handoff

Follow the exact branch/check/commit procedure in [CONTRIBUTING.md](CONTRIBUTING.md).
Record the starting public commit, requested outcome, changed paths, checks, public commit/PR URL
and remaining work. Distinguish a local draft from a published result. Never force push over
another writer. On concurrent changes, start from the new public tip and reapply your own edits.
